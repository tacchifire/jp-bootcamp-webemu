# jp-bootcamp-webemu

r0r0x-xx/JP-Bootcamp（衛星レッドチーム／ブルーチームの2日間ワークショップベンチ）を、実機の FlatSat ボードなしで使えるようにする Web エミュレータ。RP2040 向けファームウェア（PwnSat）を Renode 上で動かし、ブラウザの C3 ダッシュボードから操作する。本書は使い方をまとめる。

## 構成

| 部品 | 役割 |
|---|---|
| Renode 1.17.0 ＋ Renode_RP2040（MIT、`emu/refs/` に同梱） | RP2040 マシンのエミュレーション。ペリフェラルはソースモードで読み込む。PIO はビルド済みの PIO シミュレータ（libpiosim、MIT、Linux x86-64 用を同梱）が担う |
| 自作 USB モデル（`emu/model/`） | RP2040 USB コントローラと仮想ホスト。配布ファームの USB 列挙とデュアル CDC 接続を再現する |
| 自作 DMA 割り込み・PIO DREQ（`emu/model/`） | Renode_RP2040 の DMA に足りない割り込み（INTE/INTS と DMA_IRQ_0/1）と、PIO の TX FIFO から DMA への転送要求（DREQ）を補う。状態 LED（NeoPixel）の更新が完了するために要る。vendored のコードには手を入れていない |
| 自作 SIO スピンロック（`emu/model/`） | Renode_RP2040 の SIO スピンロックは実機と意味が違う（保持中の再取得が成功する、相手コアの書き込みで解放されない、取得に同期がない）ため、実機どおりの意味（取得は原子的で再取得不可、解放はどちらのコアの書き込みでも可）に直す。両コアが共有する USB やタイマーの状態を守るために要る。vendored のコードには手を入れていない |
| PTY ブリッジ（`emu/pty_bridge.py`） | 2本の CDC を TCP 経由で PTY 化し、実機のシリアルデバイスの代わりに安定パスで IDS へ渡す |
| Space IDS（上流、無改変） | PTY を `--port` 指定で開き、C3 とファームの間を中継する |
| PWNSAT-C3（上流、無改変） | ブラウザで使うダッシュボード（ポート8000） |
| 操作パネル（`emu/panel/`、ポート8080） | エミュレータ自体の操作（状態表示、RESET、IDS の出力表示、ファームウェアの表示・アップロード・切り替え）。C3 には手を入れないため別に置く |
| supervisor（`emu/supervisor.py`） | 上記一式の起動・状態管理・終了を行う常駐ランチャー |
| `attack.sh` | 上流の攻撃スクリプト（`attacks/`）を、IDS 経由でエミュレータへ向けて実行する入口 |

既定で起動するファームは上流の配布ファーム（PwnSat v1.0.5、noradio ビルド。以下「コース標準」）。setup が固定コミットの上流リポジトリから取得し、UF2→BIN 変換後に SHA-256 を照合する。操作パネルから別の UF2 をアップロードして切り替えることもできる（後述）。

## クイックスタート（Codespaces）

GitHub でこのリポジトリの Codespace を作成して開く。初回は devcontainer の postCreate で `emu/setup.sh` が自動で走り、Renode の取得、上流 JP-Bootcamp の clone、Python venv の構築、ファームの変換まで済ませる（ネット接続が必要）。そのあとターミナルで次を実行する。

```bash
./start-emu.sh
```

1. Codespaces のポート転送（「ポート」タブ）から 8080（Emulator panel）をブラウザで開き、状態が READY になるのを待つ。
2. 続けて 8000（PWNSAT-C3）を開く。ログインは上流の初期値（ユーザー名 `operator`、パスワード `pwnsat`。上流リポジトリで公開されている初期アカウント）。

## クイックスタート（Linux）

下の「前提」を確認してから、次を順に実行する。setup にはネット接続が必要（Renode の取得、上流リポジトリの clone、pip install のため）。

```bash
git clone https://github.com/tacchifire/jp-bootcamp-webemu.git
cd jp-bootcamp-webemu
./emu/setup.sh
./start-emu.sh
```

- setup は `./emu/setup.sh` の形で実行する（`. emu/setup.sh` のように source しない）。
- `./start-emu.sh` は setup が済んでいなければ先に setup を実行するので、`./start-emu.sh` だけでも起動できる。
- 起動したら、ブラウザで http://localhost:8080 （操作パネル）を開いて READY を確認してから、http://localhost:8000 （C3）を開く。ログインは Codespaces と同じ初期値。アクセスできるのはそのマシンの localhost からだけで、外部へ公開する仕組みはない。

### 前提

- x86-64 の Linux。
- コマンド：git、curl、tar、sha256sum（coreutils）、python3、python3-venv。Debian／Ubuntu では、setup.sh が不足分を検出すると、入れるものを表示したうえで apt と sudo で自動インストールを試みる（sudo のパスワード入力を求められる場合がある）。自動で入らない環境では、不足分と手動の導入方法を表示して止まる。手動で入れる場合は次のとおり。

```bash
sudo apt install -y git curl tar coreutils python3 python3-venv
```

- Python：目安は 3.12。setup が最後まで通ることを確認したのは Ubuntu 24.04 の python3 3.12.3 で、Codespaces の devcontainer も Python 3.12 のイメージを使う。ほかの版は確認していない。
- libstdc++ が `GLIBCXX_3.4.32` を提供すること（同梱の PIO シミュレータが GCC 13 でビルドされているため。Ubuntu 24.04、Debian 13 以降が目安）。次のコマンドで1行でも表示されれば条件を満たす。ライブラリのパスは環境により異なる場合がある（`strings` は binutils に含まれる）。

```bash
strings /usr/lib/x86_64-linux-gnu/libstdc++.so.6 | grep GLIBCXX_3.4.32
```

## 操作方法

### 起動と状態

- `./start-emu.sh` で一式が起動する。supervisor が PTY ブリッジ → Renode → IDS → C3 の順に立ち上げ、ファームの起動完了（USB 設定完了）を確認してから IDS を接続する。
- 状態は操作パネル（8080）に表示される。BOOTING＝起動中、READY＝操作可能、REBOOTING＝リセット後の再起動中、STOPPING＝終了中または再起動中。

### tmux での表示（Linux）

tmux が入っている環境で、ターミナルから（tmux の外で）`./start-emu.sh` を実行すると、tmux セッション `jp-emu` の中で起動し、そのまま画面に表示される。tmux が無い環境（Codespaces など）や、スクリプト・パイプからの起動では、これまでどおりそのターミナルで直接動く。tmux を使わずに起動したいときは `JP_EMU_TMUX=0 ./start-emu.sh`。

| ウィンドウ | 表示 |
|---|---|
| 0 supervisor | supervisor の状態表示（`emu/run/logs/supervisor.log`）。終了の操作もここで行う |
| 1 ids／2 c3／3 renode／4 console | それぞれ `emu/run/logs/` の ids.log、c3.log、renode.log、console.bin（ファームのコンソール）を `tail -F` で表示 |

- ウィンドウの切り替え：Ctrl+B のあと番号（0〜4）。一覧は Ctrl+B のあと w。
- デタッチ（動かしたまま画面から離れる）：Ctrl+B のあと d。エミュレータは動き続ける。
- 戻る：`tmux attach -t jp-emu`。`./start-emu.sh` をもう一度実行しても、動いているセッションに接続する。
- 終了：ウィンドウ0（supervisor）で Ctrl+C。supervisor が子プロセスを終了させ、セッション `jp-emu` も自動で閉じる。`tmux kill-session -t jp-emu` で閉じた場合も、同じ後始末を経て終了する。

### C3 ダッシュボード（8000）

- ボードへのコマンド送信とテレメトリ表示は C3 で行う（コマンドの使い方は上流 JP-Bootcamp のドキュメントどおり）。
- コマンドはパネルが READY になってから送ること（理由は下記の注意参照）。

### RESET（8080 パネル）

- パネルの RESET ボタンが実機の RESET ボタン相当。押すと Renode のマシンリセットと USB 再列挙が行われ、ファームが最初から起動し直す。
- リセット後は状態が REBOOTING になり、再列挙と起動完了の確認に数秒の安定待ちを加えて READY に戻る。READY に戻るまではコマンドを送らないこと。
- ファームの応答が戻らないとき（下記「攻撃スクリプト」の注意を参照）も、RESET で起動し直せる。

### IDS の出力（8080 パネル）

- パネルの「IDS の出力」欄に、Space IDS のログ（`emu/run/logs/ids.log`）の末尾200行を2秒ごとに表示する。`>> IDS` で始まる行が IDS のアラート（強調表示）。
- 同じ内容は `curl -s http://localhost:8080/api/ids-log` でも JSON で取れる。

### 攻撃スクリプト（attack.sh）

エミュレータを起動してパネルが READY になってから、別のターミナルで実行する。

```bash
./attack.sh list     # 攻撃の一覧（上流の attacks/ から生成）
./attack.sh 00       # 攻撃 00（APID の偵察）を実行
./attack.sh reset    # 攻撃で変わった基板の状態を戻す（attacks/lib/reset_bench.py）
```

- 上流 JP-Bootcamp の `attacks/` にあるスクリプトを、setup が取得したチェックアウトの中でそのまま、setup が作った venv の python で実行する（コードはコピーしない）。通信は `FLATSAT_HOST=1` で Space IDS（127.0.0.1:5010）を経由するので、攻撃は IDS に検査され、パネルの「IDS の出力」にアラートが出る。C3 は同じ IDS に接続したまま使える。
- エミュレータが起動していないとき、または READY でないときは、案内を表示して何もせずに終わる。
- 攻撃スクリプトへの引数は番号の後ろにそのまま渡せる（例：`./attack.sh 00 --end 0x05`、`./attack.sh 06 --yes`）。
- 上流の注意どおり、1本ずつ実行し、次の攻撃の前に `./attack.sh reset` で基板の状態を戻す。reset 本体（上流 reset_bench）だけでは「the position did not go back」（exit 1）になることがある。理由は2つで、どちらも実機でも起こる。(1) 確認待ちが約15秒しかなく、GPS_OVERRIDE の後の LED 点滅（エミュレータでは実時間で数十秒）より短い。(2) 基板の USB デバッグが ON の間（攻撃00・09 の後）は、基板が上りのペイロードを復号せず平文として読むため、暗号化して送られた GPS_OVERRIDE の暗号文そのものが位置として書き込まれてしまう（reset_bench の最後のコマンドでデバッグは OFF になる）。そのため attack.sh は、reset_bench の後に基板の実際の状態（位置と GS モード）を上流ライブラリで読み直して判定し、戻っていなければ reset をもう一度実行して（2回目はデバッグが OFF なので位置も正しく書き込まれる）再確認する。実状態で戻っていることが確認できれば exit 0、最後まで確認できなければ exit 1 で終わるので、そのときは1分ほど待ってからもう一度 reset を実行するか、パネルの RESET でファームを起動し直す。
- 攻撃00 は掃引の副作用で、基板の USB デバッグを ON にする（ON の間、基板は暗号化されたコマンドを平文として読み、テレメトリも平文で返す）。C3 はこれを復号できないので、PING を送っても ACK と表示されない（基板は平文の ACK を返している）。`./attack.sh reset` は最後にこれを OFF に戻す。
- **LED の点滅とエミュレータの速度（実測）**：状態 LED を点滅させる処理でファームが止まる不具合は直した（DMA の完了割り込みと PIO の DREQ をプラットフォームに追加）。ただしエミュレータは実時間の約1/20〜1/25の速さで動くため、点滅1回分（仮想時間で1.6〜3.2秒）に実時間で約40〜80秒かかり、その間に届いたコマンドは点滅が終わってから順に処理される。攻撃スクリプトは実機の速さを前提に短い待ち時間で判定するので、点滅を通るコマンドの応答を取り逃がし、silent や失敗と表示することがある。たとえば攻撃00 の全範囲の掃引は 0x007 以降の多くが silent になり、掃引の終了後も、溜まったコマンドを基板が処理し終えるまで約2分かかる（その間は PING にも応答しない）。
- 動作を確かめた攻撃は 00〜09 の全てと reset。02・05・07・08 は基板側の効果まで確認した（02 はスラスタ値の変化、05 は同一フレームの再適用、07 は secure link フラグの True→False、08 はフラッシュイメージ165オクテットの組み立て）。04 は範囲内でのセッション確立まで確認した（チャレンジへの応答で基板の認証状態が変わり、直前に拒否された SET_THRUSTER が実行された。スクリプトの短い待ち時間では応答が間に合わないため、待ち時間を延ばした測定での確認）。09 はチェーンを通しで測定し、ステップ3（デバッグ ON の間に GS_MODE でゲートを下ろす）が基板に拒否されることを確認した。理由はファームの仕様で、デバッグ ON の間は上りのペイロードを復号せず平文として読むため、暗号化して送られた解除要求の先頭バイト（0x78）が「有効化」と解釈される（上記の reset で暗号文が位置になるのと同じ仕組み）。解除要求を平文で送ればゲートは下り、後続のコマンドも実行される。したがって 09 のスクリプト自身の完走表示は、このファームでは実機でも得られない。01 は基板が応答しなくなり、パネルの RESET で復帰するところまで（実機のような自動再起動はしない）。攻撃スクリプト自身の確認表示は、実機の速さを前提にした短い待ち時間で判定するため、エミュレータでは「失敗」と表示されても基板側では効果が出ていることがある。

### ファームウェアの確認・アップロード・切り替え（8080 パネル）

- 「使用中」欄に、今の起動で書き込まれているファームのファイル名、由来（コース標準／アップロード）、サイズ、SHA-256（先頭12桁）を表示する。
- アップロード：「UF2 をアップロード」で .uf2 を選んで送る。UF2 の形式（ブロックのマジックナンバー、ブロックの欠け、RP2040 のファミリー ID、フラッシュ先頭からの配置と 2 MB 以内）を確認し、不正なファイルは拒否する。上限は 8 MiB。保存先は `emu/run/firmware/uploads/`（git の管理外）。
- 切り替え：保存済みの一覧で使いたいものの「選択」を押し、「再起動して反映」を押す。スタック（Renode・IDS・C3）が再起動し、選んだファームで起動し直す（1分前後。その間 C3 は使えない）。パネルはそのまま使える。
- コース標準へ戻すときは、一覧でコース標準を選び、同じく再起動する。選択は `emu/run/firmware/selected.json` に保存され、次回の `./start-emu.sh` でも引き継がれる。選んだファイルが消えている・不正な場合は、コース標準で起動して注意を表示する。
- 使えるのは、コースのファーム（PwnSat）を元にした RP2040 用のビルドに限る。READY の判定に、コースのファームの起動メッセージと USB のデュアル CDC を使うため。それ以外のファームは READY にならず、ERROR になる。

### 終了

- `./start-emu.sh` を実行したターミナルで Ctrl+C（tmux で動いている場合はウィンドウ0で Ctrl+C）。supervisor が自分が起動したプロセス一式だけを終了する。

## 使う上での注意と制約

| 項目 | 内容 |
|---|---|
| 起動直後の送信 | ファームの起動完了前に届いたフレームは、無応答のまま失われる（実測）。初回起動では IDS の接続自体が起動完了後になるので問題ないが、RESET 後はパネルの READY 表示を確認してから送ること |
| 切断中のコマンド | 接続が切れている間に C3 が受理したコマンドはファームへ届かず、再接続後に遅れて届くこともない（喪失する） |
| C3 の link_state 表示 | 切断検出には使えない（実測では約9秒の切断でも `connected` のままだった）。接続の実否はコマンドへの応答で判断すること |
| IDS の再接続 | 実切断の場合、IDS は元のポートを30秒窓で再オープンして自動復帰する（実測約4秒）。マシンリセット（PTY 存続）の場合は IDS から切断に見えず、そのまま通信が続く |
| BOOTSEL・ファーム差し替え | BOOTSEL（実機の UF2 書き込みモード）は再現しない。ファームの差し替えは、操作パネルのアップロードと切り替え（スタックの再起動）で行う。使えるのはコースのファームを元にしたビルドだけ |
| エミュレータの速度 | 仮想時間は実時間の約1/20〜1/25で進む。ファームの `delay()` や周期処理も、その分ゆっくり進む |
| 状態 LED を点滅させるコマンド | 処理は終わるが、点滅1回分に実時間で約40〜80秒かかり、その間は後続のコマンドが待たされる（上の「攻撃スクリプト」参照） |
| コンソール出力の停止 | 攻撃00 の処理中に、コンソール（console ウィンドウ、`console.bin`）の出力だけが止まったことが1回あった（基板はその間も応答継続）。vendored の SIO スピンロックが実機と違うことを実測で確かめ、自作モデルで実機どおりに直した。修正後は同じ手順の4回で再現していない。なお、エミュレーションを速める設定（PerformanceInMips 25。通常設定は 125）では、両方の USB 出力が止まる全停止が1回残った（原因は未特定。通常設定では観測されていない）。コンソールを戻すには、パネルの RESET でファームを起動し直す |
| GPIO ボタン | 実機基板の BUTTON1/2（GPIO12/13）は配布ファームが読まないため、操作対象にしていない |
| センサー・無線 | 加速度・気圧などのセンサーと無線はエミュレーション対象外。起動ログにセンサー未検出のエラー行が出るのは想定どおりで、初期化はそのまま進む |
| 到達範囲 | 転送・公開されるのは C3（8000）と操作パネル（8080）だけ。Renode はコンソールモードでサーバポートを開かず、ブリッジの TCP は loopback のみ |
| 演習の動作範囲 | C3→IDS→ファームのコマンド往復（PING に対する ACK）と再接続、`attack.sh` による攻撃00・03・06 と reset の実行までは実測済み。各演習（攻撃10本）の成否までは保証しない |
